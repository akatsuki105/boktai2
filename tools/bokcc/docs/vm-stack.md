# VM のスタックとフレーム

`.bokc` の `p0` や `v1` が実行時に何を指しているかをまとめる。
文法そのものは [syntax.md](syntax.md) を参照。

VM の状態は `gVM` (`0x030045A0`, 240バイト) 1つだけに入っている。
再入はしない作りで、スクリプトの入れ子はこの中のスタックで表現される。

| オフセット | フィールド | 役割 |
| --- | --- | --- |
| `0x00` | `pc` | 現在読んでいるバイト位置。1本しかない |
| `0x04` | `result` | 直前の文の値。`.bokc` の `result` |
| `0x08` | `subroutineStackTop` | サブルーチンスタックの先 |
| `0x0C` | `subroutineStack[24]` | 制御命令のラベル開始位置 |
| `0x6C` | `scriptStackTop` | スクリプトスタックの先 |
| `0x70` | `scriptStack[32]` | 引数記述子とローカル変数の置き場 |

`VM_ResetStacks` が両方を空に戻す。VM の初期化 (`FUN_08231bec`) から呼ばれる。

## スクリプトスタック

スクリプト1本の呼び出しにつき1フレーム積まれる。フレームには
**引数記述子へのポインタ1語**と、**そのスクリプトが使うローカル変数の語**が入る。
引数の値そのものはフレームに入らない。呼び出し側のC側スタックにある `argv` を
`ScriptArgs` 経由で間接的に読む。

積むのは `VM_PushScriptFrame(args, idx)`、戻すのは `VM_PopScriptFrame` である。
`idx` がローカル変数の個数で、変数の語を先に確保してから引数記述子を置き、
`scriptStackTop` をその直後に進める。

```
                  低位 ←                                      → 高位
  scriptStack:  ... [ v3 ][ v2 ][ v1 ][ ScriptArgs* ][ 次のフレーム ...
                     ^ 呼び出し前の scriptStackTop    ^ 呼び出し中の scriptStackTop
```

`scriptStackTop` から**手前に向かって**数えるので、

| `.bokc` | 読み方 | 実際の位置 |
| --- | --- | --- |
| `p0` `p1` ... | `VM_ParseParameter(n + 1)` | `(*(scriptStackTop - 1))->argv[n]` |
| `result` | `VM_ParseParameter(0)` | `gVM.result` (フレームとは無関係) |
| `v1` `v2` ... | `VM_GetVariable(n)` | `*(scriptStackTop - 1 - n)` |

`VM_GetVariable(0)` は引数記述子のポインタそのものを読んでしまうので、
変数は `v1` から始まる。実際 ROM のスクリプトに `v0` は1つも出てこない
(使われているのは `v1` から `v7` まで)。

変数への代入は式の中でしかできない。`VM_RunExpression` が代入演算子を見たとき、
左辺の opcode が `0x90` なら `VM_StoreVariable`、メモリ参照なら `VM_StorePointer` に振り分ける。

### 変数スロットの個数

`idx` は `VM_ExecByID` が `VM_LookupByID` 経由で渡す値で、
`ScriptDirectory.script_entries` のエントリの**上位8bit**である
(下位24bitがバイトコードのオフセット)。
つまりスクリプトごとに「変数をいくつ使うか」が ROM に書いてある。

根拠として、`scripts.bokc` で `vN` を使っている501本すべてで
上位8bit が `max(N)` 以上になっている (493本は一致、12本は確保だけして使っていない)。
上位8bit の分布は 0 が 11034本、1 が 421本、以下 7 まであって最大は 7。

`scriptStack` は32語しかないので、入れ子の全フレームの
(変数の個数 + 1) の合計がこれを超えられない。

### フレームが積まれない場合

`VM_PushScriptFrame` は `args` が `NULL` だと何もせずに `NULL` を返す。
`if` や `switch` の節の実行 (`VM_ExecBlock(block, NULL, 0)`) や、
式の中に置かれたブロックの実行はこの形なので、フレームは積まれない。
だから節の中からでも、外側のスクリプトの `p0` や `v1` がそのまま見える。

スクリプトとして呼ばれた場合は、`VM_Exec` が `args == NULL` を
`sEmptyArgs` (引数0個) に差し替えるため、必ずフレームが積まれる。

## サブルーチンスタック

サブルーチンが名前付き引数 (`.n = 16` など) を探すための位置を覚えておくスタック。
`0x60` のディスパッチ1回につき1語で、`if` のような命令側のサブルーチンでも積まれる。
`gSubroutineTable` 側は自分では積まず、呼び出した `0xB745` / `0x9906` の分を使う。

`VM_RunControl` はハンドラを呼ぶ前に、オペランドの終わり = ラベルが
始まる位置を `VM_PushSubroutineStack` で積み、ハンドラから戻ったら `VM_PopSubroutineStack` で捨てる。
`VM_SeekToNamedArg` は毎回この**最上位の位置から**読み直して目的の文字を探す。

そのため、ハンドラは自分のラベルだけを見ることができ、
同じラベルを何度でも、どの順番でも読める。
24語あるので、制御命令の入れ子はその深さまで。

## 式の評価スタック

`VM_RunExpression` のローカル配列 `ExprSlot stack[8]` で、`gVM` には入っていない。
逆ポーランド記法で並んだオペランドを積み、演算子で2つ取り出して結果を積み直す。

スロットは値と**そのオペランドのバイト位置**の組になっている。
代入の左辺をどこに書き戻すかは、この位置を見て決める。
深さが8しかないので、式の入れ子もそこまでである。

## pc の扱い

`pc` は1本しかない。制御命令のハンドラは `VM_GetValue` を呼ぶたびに
`pc` を進めながらオペランドを読み、`VM_SeekToNamedArg` はそれを上書きする。

`VM_GetPC` は、`pc` が終端 (`0x00`) かラベル (`0x50`) を指していると `NULL` を返す。
ハンドラが可変個のオペランドを読むループはこれで止まる
(`VM_Ctrl_22FF` や `VM_Ctrl_CallIndirect` がその形)。
位置引数の列はラベルの手前で終わる、ということでもある。
