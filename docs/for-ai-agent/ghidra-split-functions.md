# Ghidra functions that are not functions

Ghidra sometimes creates a function at an address that is really just a
**branch target inside another function** — most often a shared epilogue.
The repository's disassembly is already correct in these cases (the address is
a plain local label such as `_080FF04C:` inside the parent's
`asm/func/*.inc`), so this is a Ghidra-side defect only.

**Why it happens:** in Thumb, a branch further than ±2 KB is assembled as
`bl`. Ghidra's analyzer reads `bl` as a call, so every long backward branch to
a function's own epilogue looks like a call to a new function, and it creates
one there. The parent function's body then *stops* before that address, which
is the visible symptom.

**Why it matters:** the parent's body is truncated, so its decompile is cut
short and `check_decomp.ts` reports raw offsets that are really just the
missing tail. It also produces a fake `FUN_xxxxxxxx` that a later
`todo-to-naked` pass will happily promote into a bogus C stub.

## Detecting them

Compare Ghidra's function entry points against the built symbol table. The
repo covers the whole ROM, so a Ghidra function with no symbol in
`boktai2.sym` is a candidate. Note that `boktai2.sym` stores Thumb addresses
with the Thumb bit **set**, so mask bit 0 before comparing.

```sh
G=http://127.0.0.1:8089
curl -s "$G/list_functions?offset=0&limit=20000" | awk '{print tolower($NF)}' | sort -u > /tmp/gfn.txt
python3 -c "
import io
for line in io.open('boktai2.sym', encoding='utf-8', errors='replace'):
    f = line.split()
    if len(f) >= 3 and f[1] in ('T', 't'):
        print('%08x' % (int(f[0], 16) & ~1))
" | sort -u > /tmp/rthumb.txt
comm -23 /tmp/gfn.txt /tmp/rthumb.txt
```

`boktai2.sym` is only regenerated by a build, so run `make` first.

Not every hit is this defect — ARM-state code and library regions also show
up. Confirm each one before touching it: the giveaway is a tiny body (a few
instructions ending in `pop`/`bx`) immediately after the parent's body ends,
with the parent branching to it.

## Fixing one

**The order matters.** Deleting the function first does not work: Ghidra sees
the still-pending `UNCONDITIONAL_CALL` references and immediately recreates a
function at the branch target (observed on `FUN_080ff048`, which came back as
`FUN_080ff04c`). Retype the references first.

1. Retype every `UNCONDITIONAL_CALL` reference aimed at the address to
   `RefType.UNCONDITIONAL_JUMP` with `SourceType.USER_DEFINED`
   (`ReferenceManager.delete` then `addMemoryReference`, keeping the operand
   index). References Ghidra already classified as `UNCONDITIONAL_JUMP` are
   fine as they are.
2. `FunctionManager.removeFunction(addr)`.
3. Extend the parent with `Function.setBody(oldBody ∪ [start, end])`.
   `end` is the parent's last instruction, **not** the next function's entry —
   trailing pool constants are data and stay outside the body, the same as
   every other gap in a fragmented body.

Guard the script on the exact "before" state (parent name, parent's current
max address, the fake function's exact body range) and verify that the range
belongs to nobody before calling `setBody`. Verify the decompile afterwards —
it should have no call to the deleted name, no `halt_baddata`, and a normal
`return` at the end — and only then `POST /save_program`. A
`Possible PIC construction ... Changing call to branch` warning in the
decompile output is the expected result of step 1, not a problem.

## Fixed so far

| Fake function | Parent | Body added |
|---|---|---|
| `FUN_080ff048` | `FUN_080fe7f4` | `[080FF048, 080FF05B]` |
| `FUN_080fe198` | `FUN_080fd08c` | `[080FE198, 080FE1A7]` |

`FUN_080ff048` also needed a repository-side fix, because the extraction had
already split it into its own `asm/func/FUN_080ff048.inc`: its contents were
appended to `asm/func/FUN_080fe7f4.inc`, a `_080FF048:` label was added, and
the one `bl FUN_080ff048` became `bl _080FF048`. It stays `bl` — rewriting it
as `b` would change the instruction length and break the match.
`FUN_080fe198` needed no repository change; the repo already had it as a label.
